## Постоянные правила (для всех задач)

- Не объявлять PASS без реального лога и файла результата.
- Не писать «готово», пока не проверено командой.
- Любая долгая команда: заданный таймаут, условие выхода и вывод прогресса в файл лога.
- После ошибки не повторять ту же команду более одного раза: сначала прочитать сообщение об ошибке и записать урок.
- Не менять и не удалять чужие файлы проекта. Только `audit/`. Перед заменой своего файла делать копию в `audit/backups/<UTC-время>/`.
- Если не уверен в версии, лицензии или параметре — проверить по первоисточнику, а не по памяти.
- Каждый ответ пользователю: что сделано, что проверено командой, что не проверено.

## Записи

### L1 — Цикл опроса без выхода при завершении (2026-11-13)
- Что произошло: для опроса Kaggle был запущен `for i in $(seq 1 18); do kaggle kernels status ...; sleep 30; done`. Статус `KernelWorkerStatus.COMPLETE` вернулся сразу (04:06:44), но цикл продолжал опрашивать до конца всех 18 повторов (до 04:13:57, около 7 минут впустую). Причина остановки — внешний таймаут команды (SIGTERM, exit 143).
- Причина: в цикле не было условия выхода по терминальному статусу; условие `grep` искало строку в другом формате (`status "complete"` вместо `KernelWorkerStatus.COMPLETE`).
- Последствие: ~7 минут лишнего ожидания, exit code 143 вместо нормального завершения.
- Правило на будущее: любой опрос статуса писать как цикл с выходом по терминальному статусу и предельным сроком. Образец:
  `end=$((SECONDS+1800)); while [ $SECONDS -lt $end ]; do s=$(kaggle kernels status <ID> 2>&1); echo "$(date -u +%T) $s"; case "$s" in *KernelWorkerStatus.COMPLETE*|*KernelWorkerStatus.ERROR*|*KernelWorkerStatus.CANCEL*) break;; esac; sleep 30; done`.
  Запрещены циклы фиксированной длины без условия выхода.
- Как проверять: в команде опроса есть `break` по терминальному статусу и предельный срок; в логе виден выход сразу после первого COMPLETE.

### L2 — COMPLETE не равно «результат получен и корректен» (2026-11-13)
- Что произошло: статус `KernelWorkerStatus.COMPLETE` означает только, что скрипт завершился на стороне Kaggle. Он не гарантирует наличие ожидаемых файлов, их размер, читаемость JSON и успешность проверок внутри скрипта.
- Причина: статус платформы и содержимое результата — разные вещи; сам скрипт может завершиться с внутренним FAIL/BLOCKED.
- Последствие: при доверии одному статусу возможен ложный PASS без лога и артефактов.
- Правило на будущее: после COMPLETE обязательно скачать результат (`kaggle kernels output <ID> -p <папка> -o`), проверить, что ожидаемые файлы существуют, имеют ненулевой размер и открываются, прочитать лог и внутренний summary. Только после этого писать PASS. Если файла или поля нет — BLOCKED или FAIL с указанием, чего именно нет.
- Как проверять: в отчёте для каждого PASS указан путь к скачанному файлу и фрагмент лога; JSON проходит `json.load` без ошибок.
### L3 — Неверный шаблон raw.githubusercontent URL (2026-11-13)
- Что произошло: в `collect_licenses.py` URL собирался как `https://raw.githubusercontent.com/{repo}/raw/{sha}/{file}`. Все 15 GitHub LICENSE были сохранены как MISSING (404). Ручная проверка `curl` показала, что корректный URL — `https://raw.githubusercontent.com/{repo}/{sha}/LICENSE` (HTTP 200, 1062 байта для hzwer/Practical-RIFE).
- Причина: лишний сегмент `/raw/` в шаблоне; шаблон не был проверен на одном компоненте до массового запуска.
- Последствие: повторный прогон сборщика лицензий и временно пустые `LICENSE-code.txt` в 15 компонентах.
- Правило на будущее: перед массовым сбором проверить шаблон URL на одном известном файле и убедиться в HTTP 200.
- Как проверять: `curl -sSL -o /dev/null -w '%{http_code}\n' '<url>'` возвращает 200 до запуска цикла по всем компонентам.

### L4 — Пробел в имени файла curl и HTML с ключами (2026-11-13)
- Что произошло: `curl -o "audit/provenance/kaggle_efficient_gpu_usage Wayback.html"` содержал пробел в имени выходного файла; HTML-код (20 КБ, с `<script>` и site key) был напечатан в stdout, файл не создан. Дополнительно выяснилось, что архивная копия `kaggle.com/docs/notebooks` — это SPA-оболочка без содержимого документации.
- Причина: имя файла с пробелом и без проверки результата; архив не содержит server-rendered текста.
- Последствие: лишний вывод в лог и риск попадания site key в коммит.
- Правило на будущее: имена файлов без пробелов; после скачивания проверять, что файл непустой и содержит ожидаемый текст; HTML с `<script>`/ключами не коммитить, удалять после извлечения текста.
- Как проверять: `test -s <file>` и `grep -c '<script' <file>`; при наличии скриптов файл удаляется до `git add`.

### L5 — `$?` после пайпа (2026-11-13)
- Что произошло: `git fetch --all --prune 2>&1 | tail -30; echo "FETCH_EXIT=$?"` — переменная `$?` содержала код завершения `tail`, а не `git fetch`.
- Причина: после конвейера `$?` относится к последней команде конвейера.
- Последствие: нельзя было утверждать, что fetch успешен; потребовался повторный запуск `git fetch` с проверкой кода.
- Правило на будущее: не проверять `$?` после пайпа; использовать `${PIPESTATUS[0]}` или перенаправление вывода в файл с последующей проверкой `$?`.
- Как проверять: `git fetch ... > /tmp/opencode/fetch.log 2>&1; echo "EXIT=$?"` возвращает реальный код git.

### L6 — Лицензия по полю model card не равна лицензии весов (2026-11-13)
- Что произошло: для CosyVoice 3, Kokoro, Whisper, Depth Anything V2, Video Depth Anything в model repo нет отдельного файла лицензии; лицензия известна только из поля `license:` model card.
- Причина: поле model card — это метаданные, а не текст лицензии на конкретный файл весов.
- Последствие: возможна выдача лицензии весов за подтверждённую без текста и без права на коммерческое использование.
- Правило на будущее: записывать `"license_basis": "model_card_metadata"` и статус `"условный PASS"` (conditional PASS), не считать это окончательным PASS; при наличии текста лицензии — статус PASS и путь к LICENSE-weights.txt.
- Как проверять: в audit/licenses/STATUS.json для таких компонентов есть license_basis=model_card_metadata и license_status="CONDITIONAL PASS"; для компонентов с текстом лицензии указан путь к файлу.

### L7 — CANCEL_ACKNOWLEDGED без сообщения (2026-11-13)
- Что произошло: Kaggle-ноутбук P0 RIFE (v1 и v2) менял статус RUNNING -> CANCEL_ACKNOWLEDGED примерно через 90 секунд после старта. Логи обрывались на установке зависимостей/скачивании; сообщения об ошибке не было. Диагностика: CPU-only kernel COMPLETE (~2.5 мин), GPU-only kernel COMPLETE (~42 с), GPU+internet kernel COMPLETE (~3 мин), uv+torch kernel COMPLETE (~4.5 мин), gdown-скачивание 4.25 COMPLETE (~1.5 мин).
- Причина: не установлена. Исключены: отсутствие GPU, отсутствие интернета, uv, torch, Google Drive. Остаётся внешняя причина (преэкшн/лимит аккаунта) либо ресурсный watchdog; требует проверки в веб-интерфейсе Kaggle.
- Последствие: два GPU-запуска потеряны; RIFE не протестирован.
- Правило на будущее: при CANCEL_ACKNOWLEDGED сохранить лог, запустить минимальный GPU+internet диагностический kernel и не повторять тяжёлый kernel более одного раза; при повторе — BLOCKED с указанием общего внешнего признака.
- Как проверять: в логе есть переход в CANCEL_ACKNOWLEDGED; рядом лежат результаты diag_cpu/diag_gpu/diag_gpu_net/diag_uv/diag_gdown с COMPLETE.

### L8 — `kaggle kernels output` без фильтра тянет весь /kaggle/working (2026-11-13)
- Что произошло: после LTX-рана `kaggle kernels output <id> -p ... -o` без `--file-pattern` начал скачивать содержимое `/kaggle/working`, включая venv с torch (файлы `audit/envs/ltx/bin/*`), и был прерван таймаутом; повторные попытки получили `429 Too Many Requests` от Kaggle API.
- Причина: venv, репозиторий и кэши были созданы внутри `/kaggle/working`; API выгружает всё содержимое без фильтра.
- Последствие: потеря времени на загрузку, rate limit, риск превысить лимит 20 ГБ и получить неполные артефакты.
- Правило на будущее: venv/репозитории/веса/кэши держать вне `/kaggle/working` (например `/tmp/audit/...`), в `/kaggle/working` — только evidence; скачивать результат с `--file-pattern` (regex), например `--file-pattern '.*\.log$'`.
- Как проверять: `du -sh /kaggle/working` в ноутбуке — только logs/results/config; в downloaded-папке нет `envs/`, `repos/`, `weights/`.

### L9 — CosyVoice: пять последовательных падений из-за окружения и формата промпта (2026-11-13)
- Что произошло: CosyVoice 3 падал пять раз: (1) сборка openai-whisper без `pkg_resources`; (2) `ModuleNotFoundError: onnxruntime`; (3) `ModuleNotFoundError: whisper`; (4) `en_core_web_sm` не установлен; (5) `AssertionError: <|endofprompt|> not detected`; (6) chunking дал 1 чанк на 9552 символа из-за двойного слеша в regex (`\\s` вместо `\s`).
- Причина: официальный requirements не ставился целиком (фильтр), build-зависимости не установлены, пример из model card не воспроизведён дословно, regex собран с двойным escape.
- Последствие: 5 лишних Kaggle-рана (~20 минут GPU и ожидания).
- Правило на будущее: перед тяжёлым прогоном (а) прочитать официальный inference-пример и скопировать формат промпта/токены, (б) проверить импорты, (в) проверить regex на одном абзаце локально, (г) для sdist ставить `setuptools<81 wheel` и `--no-build-isolation-package`.
- Как проверять: в логе `chunking.chunks > 1` и `max_chars <= 300`; prompt содержит `<|endofprompt|>`; установка requirements завершилась rc=0.

### L10 — `huggingface-cli` больше нет: в huggingface_hub 1.x/2.x команда называется `hf` (2026-11-14)
- Что произошло: в ноутбуках P1 скачивание весов шло как `{env}/bin/huggingface-cli download ...`. Установка `huggingface_hub[cli]` прошла с предупреждением «does not have an extra named cli», после чего ноутбук упал: `/bin/sh: 1: .../huggingface-cli: not found` (rc=127), статус BLOCKED.
- Причина: в новых huggingface_hub CLI переименован в `hf`, а extra `cli` удалён; старый бинарь не создаётся.
- Последствие: потерян один прогон Video Depth Anything (v1), потрачено ~1 мин GPU.
- Правило на будущее: не писать `huggingface-cli` и не ставить `huggingface_hub[cli]`. Ставить `huggingface_hub`, затем выбирать бинарь: `hf` если `{env}/bin/hf` существует, иначе `huggingface-cli`. Проверять `rc` и наличие файла после скачивания.
- Как проверять: в логе `.../bin/hf download ... -> rc=0` и скачанный файл существует (в v2 vd: `download_model rc=0`, чекпоинт на месте).

### L11 — Неполный requirements у Wan2.1: einops не объявлен, flash_attn не собирается (2026-11-14)
- Что произошло: v1 — `uv pip install -r requirements.txt` падает на `flash_attn` (нет колеса под torch 2.6/py310, sdist вызывает `setup.py`, который импортирует torch в build isolation: `ModuleNotFoundError: No module named 'torch'`). v2 — после фильтрации `flash_attn` установка прошла, модель скачалась (22 файла, 83 с), но `generate.py` упал: `ModuleNotFoundError: No module named 'einops'` в `wan/modules/vae.py:8`.
- Причина: `flash_attn` в requirements опционален (есть fallback на SDPA), а `einops` вообще отсутствует в requirements, хотя код его импортирует. Официальный requirements неполон.
- Последствие: два GPU-рана (~1.8 мин) без результата; компонент BLOCKED (лимит в одну попытку восстановления).
- Правило на будущее: перед тяжёлым прогоном проверять не только формальную установку requirements, но и фактические импорты пакета (`grep -r "^import \|^from " <pkg> | sort -u`) и добавлять недостающие зависимости в venv. Для `flash_attn` использовать `--no-build-isolation-package flash-attn` + `ninja` + `setuptools<81 wheel` **или** фильтровать строку, если пакет опционален (проверить `try/except ImportError` в коде).
- Как проверять: в логе `python -c "import wan"` проходит (rc=0) до запуска `generate.py`.

### L12 — Depth Anything V2: неверный вызов pipeline и вырожденный вход (2026-11-14)
- Что произошло: v1–v5 падали `TypeError: DepthEstimationPipeline.__call__() missing 1 required positional argument: 'inputs'` (вызов `pipe(images=im)`). После исправления на `pipe(inputs=im)` (v6) прогон PASS, но все 10 сохранённых карт глубины были идентичны и полностью чёрные: синтетический вход (горизонтальный градиент + шахматка + равномерный шум) давал постоянную глубину, а нормировка `(d - d.min())/(d.max() - d.min() + 1e-8)` при `d.max()==d.min()` даёт нули.
- Причина: (1) скопирован не тот именованный аргумент; (2) вход не имел смысла для модели, а проверка PASS смотрела только на `np.isfinite`, но не на `std` карты.
- Последствие: 6 бесполезных прогонов, превью-заглушка.
- Правило на будущее: сигнатуру вызова брать из официального примера модели, а не из памяти; в проверку качества добавлять `std(depth) > eps` и `len(unique(vis)) > 10`, иначе PASS фиктивен.
- Как проверять: `summary.json` содержит `range` и ненулевой `std`; PNG открывается и имеет >10 уникальных значений.

### L13 — Парсер nvidia-smi ожидал три колонки, а запрос был на одну (2026-11-14)
- Что произошло: для замера VRAM запускалось `nvidia-smi --query-gpu=memory.used --format=csv,noheader -l 1`, а `max_gpu_mib()` парсит `split(",")` и требует `len(parts) >= 3` (`parts[2].endswith("MiB")`). Файл собирался, но возвращался `None` — поле `peak_vram_mib` в summary оказалось `null` (Video Depth Anything v2).
- Причина: несоответствие формата запроса и парсера; helper проверялся только на логах Stage A/B, где запрос был трёхколоночным.
- Последствие: у одного компонента нет измерения VRAM; повторный прогон не делался (лимит попыток).
- Правило на будущее: использовать тот же запрос, что и парсер: `nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used --format=csv,noheader -l 1`. Перед вызовом проверять парсер на одном примере строки.
- Как проверять: в `summary.json` `peak_vram_mib` — число, а не `null`.

### L14 — Захардкоженный dtype вместо измеренного (2026-11-14)
- Что произошло: в Parakeet-ноутбуке поле `dtype` задавалось строкой `"FP16"` в `finish()` независимо от фактического режима. В логе нет ни `float32`, ни `autocast`, так что заявленный dtype не подтверждён (скорее FP32: веса 0.6B и пик 4.85 ГБ).
- Причина: значение-заглушка попало в отчёт как факт.
- Последствие: в таблице dtype Parakeet помечен как «не измерено».
- Правило на будущее: dtype измерять, а не объявлять: `str(next(model.parameters()).dtype)` после загрузки (как сделано в Depth Anything V2 и SDXL). Если измерить нельзя — писать `null` + «not measured».
- Как проверять: в `summary.json` `metrics.dtype` — реальный `torch.float32`/`torch.float16`, полученный из модели.

### L15 — Для DeepFilterNet3 официальный путь — CLI `deepFilter`, а не ручной ONNX (2026-11-14)
- Что произошло: первая версия ноутбука скачивала `DeepFilterNet3_onnx.tar.gz` и пыталась подать сырой звук в `onnxruntime`. Модель ожидает вход `emb` формы `[1, 'S', 512]` (эмбеддинги, а не waveform), скрипт упал `ValueError: negative dimensions are not allowed`. Официальный README предлагает `pip install deepfilternet` и `deepFilter noisy.wav --output-dir <dir>`.
- Причина: dогадка о формате входа вместо чтения официального примера; ONNX-экспорт не включает STFT/ERM-фичи.
- Последствие: один потерянный ран, затем PASS за 6.8 с (RT 0.019) с официальным CLI.
- Правило на будущее: если в репозитории есть pip-пакет и CLI-пример — использовать его; ручной ONNX только если это единственный путь и формат входа подтверждён `sess.get_inputs()`.
- Как проверять: в логе `INFO | DF | Using DeepFilterNet3 model ...` и `Enhanced noisy audio file ... (RT factor: 0.019)`.

### L16 — pip install torch==X не заменяет системный torch на Kaggle; transformers 5.x несовместим с torch 2.11 (2026-11-14)
- Что произошло: в Wan2.2 TI2V-5B GGUF ноутбуке выполнялось `pip install torch==2.6.0 ... --index-url .../cu126` (rc=0), но `import torch` всё равно возвращал 2.11.0+cu130 (Kaggle pre-installed). Затем `pip install git+diffusers` подтянул transformers 5.20.2, который при импорте требует `torch._C._dynamo.eval_frame.skip_code` — символа, отсутствующего в torch 2.11, и падал `ImportError`/`RuntimeError`. Первый прогон (v1) заблокирован.
- Причина: pip не перезаписал системный torch (вероятно, Kaggle держит его в системном пути); версии transformers/diffusers не были закреплены и уехали в несовместимые.
- Последствие: потерянный прогон + ~16 ГБ повторной загрузки; исправление — не трогать torch, закрепить `diffusers==0.35.2` и `transformers==4.51.3` (v2).
- Правило на будущее: на Kaggle не переустанавливать torch; использовать предустановленный и подбирать diffusers/transformers под него. Фиксировать версии явно (`==`), проверять `import` после установки одной строкой `python -c "import torch,diffusers,transformers; print(...)"` до скачивания весов. Для T4 (sm_75) flash_attn не ставить — SDPA по умолчанию.
- Как проверять: в `summary.json` `versions.torch` == предустановленная (2.11.0+cu130), `versions.transformers` == 4.51.3, импорт diffusers успешен до шага загрузки весов.
